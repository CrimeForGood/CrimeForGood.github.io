We do what attackers do first. Then we tell you.

crimeforgood finds leaked keys, booby-trapped repos and hacked sites the way an attacker would, then reports them instead of using them. We read public code and systems we're hired to test; we don't break into anything. The lists and the tools are open source.

Same playbook, different ending

Attackers sweep for what's left open and probe what's meant to hold. So do we. The difference is what happens next.

  • Open lists and tools

    We scan public GitHub repositories and publish what we find: repos built to harm you, and repos that will leave you exposed. Anyone can download the lists and run the tools.

    Building now

  • Telling the victims

    Threat feeds block hacked sites as if they were malicious, and nobody tells the owner. A dentist whose site is serving injected phishing links needs to hear about it, not just land on a blocklist.

    Planned

  • Research without the spotlight

    Plenty of skilled researchers skip bug bounties because they don't want their names known. Companies hire crimeforgood for agreed security work and deal only with us; the researchers do it as our contractors, and the client never learns who they were.

    In development

  • A red-team harness anyone can run

    The tools that stress-test AI models cost enterprise money, and the attacks baked into them aren't that sharp. We're building an open harness of real adversarial prompts that runs against any model through its API. You pay for the tokens, not the licence.

Two lists, kept apart

A repo that attacks you and a repo with a bug in it are different problems. They get different lists, different evidence and different publishing rules.

Malicious

Repos written to hurt whoever runs them: typosquats, credential stealers, backdoored forks, fake exploit code that carries a payload.

Published
As soon as the evidence is recorded
What to do
Don't clone it, don't install it

Vulnerable

Honest projects with a flaw that puts their users at risk: leaked secrets, known-vulnerable dependencies, unsafe defaults. Not bad, but worth knowing about.

Published
After the maintainer has been told and had time to fix it
What to do
Pin, patch or wait for the fix

Every entry shows its evidence

A listing is a claim about someone's code, so each one says which rule fired, on which commit, in which file. If you can't reproduce it, it shouldn't be there.

These are example records with made-up repos. Field names may change before the first release.

list        malicious
repo        github.com/example-user/reqeusts-toolkit
finding     Install script sends environment
            variables to a remote host
rule        install-hook-exfiltration
commit      3f9a1c2
file        setup.py, line 14
first seen  2026-01-01
status      published
list        vulnerable
repo        github.com/example-org/invoice-service
finding     Live cloud access key committed
            to the repository
rule        committed-secret
commit      b71e0d4
file        config/deploy.env, line 3
first seen  2026-01-01
status      maintainer notified, not yet public

How a repo gets listed

  1. Scan

    Open source rules run against public code on GitHub. We read repositories. We don't probe anyone's live systems.

  2. Record the evidence

    A finding only counts with the rule, commit, file and line attached, so anyone can check it.

  3. Tell the maintainer

    For vulnerable repos, the maintainer hears first and gets time to fix it. Malicious repos skip this step.

  4. Publish

    The entry goes on the open list, free to download and build on.

  5. Correct

    Anyone can dispute an entry. Fixed repos come off the vulnerable list, and mistakes are removed in public.

Listed by us, or worried you will be?

A listing is public and it's about your code, so you get a direct line to challenge it. Here is what to do, and what we don't do.

Dispute an entry
If you maintain a repo we listed and think we're wrong, or you've fixed it, open an issue with the repo and the entry. We re-run the rule against the current code. If it no longer fires, the entry comes off. If we listed it in error, the removal says so.
Seen us in your logs?
You haven't. The scanner reads public repositories on GitHub; it doesn't crawl or probe anyone's servers, so there is no crimeforgood traffic to find and nothing to opt out of. If that ever changes, this page will say so first, with a way to identify our requests and ask them to stop.
Found a problem in our tools
A private security contact is being set up and will be published here. Until then, open an issue asking for a private channel. Don't put exploit details in it.
Hired work only
Beyond public code, we only test systems whose owners have engaged us in writing. Nothing on this site is an offer to test anyone else's.
